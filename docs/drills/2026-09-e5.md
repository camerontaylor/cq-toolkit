## Goal (ws-e acceptance)

End-to-end against a scratch GitHub repo (integration lane, dispatch-gated):
a seeded review thread gets fixed, replied, and resolved by the SHIPPED
`runReviewLoop`; a re-run is a true no-op (zero fix jobs, zero gh
mutations, verify stage never runs). The loop closes with a non-privileged
arbitrary reviewer's thread — the market-gap scenario — riding plain gh
REST/GraphQL (reply + resolve), no admin surface anywhere.

## Deviation record (single identity, recorded)

The drill holds exactly ONE GitHub identity, so the seeded review thread is
created via the REST API under the SAME token identity that authored the PR
— a stand-in reviewer, not a second account. The fixture flag is
`REVIEWER_ROLE_SIMULATED = true`
([test/e2e/helpers/review-live.ts](../../test/e2e/helpers/review-live.ts)),
asserted in the live test, and this paragraph is the human-readable record.

Consequence handled as data: the seeded thread's author IS the responder
(`pr-author`), so the live loop runs with
`classifyConfig: { ...defaultLoopClassifyConfig,
skipResponderAuthoredThreads: false }` — the shipped default would classify
the thread `skip` (`responder_authored`) before any job is planned. This is
a per-drill classifyConfig flip (R3 data), never a code change; deriving
from the loop default keeps its sticky/self-reply suppression.

## Fixture inventory (what one dispatch creates/leaves)

- Repo `cq-scratch-e5-<run_id>` (private, auto-initialized) — LEFT BEHIND.
- Per run: one branch `e5-fixtures-<run_id>-<ts>` + its own PR to the
  default branch; `reviewed.txt` line 3 carries `typo-target: applee`. Each
  dispatch leaves one branch + PR + thread + comment per run in the scratch
  repo (by design — zero cross-run coupling; the owner deletes the repo by
  hand).
- One REST review comment (the thread) anchored on that line at the seeded
  head — `reviewerRoleSimulated: true`.
- One REST top-level issue comment (round-1 medium): reviewer feedback
  needing a response but no code change ("Reviewer note: also mention in
  the README that the fruit is an apple."). With it, run 1 plans TWO jobs
  and posts THREE actions, and run 2 live-proves the leading-signature
  suppression on the loop's own issue_comment reply.
- After run 1: a fix commit on the PR branch, one reply on the thread, one
  response under the comment, the thread resolved, the dispatch log's
  three actionIds recorded.
- Run 2 mutates nothing (zero gh mutations asserted from the recorded argv).

## How to dispatch

```sh
gh workflow run live-review --ref <branch-with-the-workflow> -f run_id=<fresh-id>
gh run watch   # or: gh run list --workflow=live-review
```

Requirements: repo Actions secret `GH_TOKEN` (repo scope, same identity the
drill records); dispatch-only by construction — never fires on push/PR.
The vitest leg runs from source with `LIVE_GH=1`; the precondition step
refuses a misconfigured dispatch loudly instead of reporting green-skipped.
