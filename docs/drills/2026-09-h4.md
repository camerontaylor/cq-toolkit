## Drill (b) — divergence: force-diverge the queue, classify, recover

1. Force-diverged the queue: `git push --force origin diverge:refs/heads/merge-queue`
   where `diverge` = `14a7027` (old main) + one unrelated commit → queue `bad0622`.
2. Classification (sync-merge-queue triage): `merge-base --is-ancestor` both ways →
   neither main ⊆ queue nor queue ⊆ main → **DIVERGED**.
3. Recovery per the sync doctrine (merge-commit + conflict handling): `git merge
--no-ff origin/main` on the queue → merge commit `4ec51d0` (no conflicts here —
   the histories touch different files; the template's conflict path aborts and
   escalates needs-human, not needed in this drill).
4. Post-recovery verification: main IS ancestor of the queue again; queue pushed

## Incident found and fixed during the drill (recorded for the doctrine)

The first `static.yml` instantiation failed GitHub's workflow parser at
**startup** (run created, 0 jobs, no logs, run named by file path) because the
YAML was invalid, not merely unusual. Bisected with probe workflows: the poison
was a **colon + space inside a plain-scalar `run:` value** (`run: echo "static:
always reports (I4 self-test)"` — `static: ` is a mapping-value indicator
mid-scalar; the quotes are ordinary characters inside a plain scalar, so they
protect nothing). Fix: keep `:` out of unquoted step values or quote the entire
value (`run: 'echo …'`). YAML 1.2 plain scalars may carry `:` only when it is not
followed by a space; a line break is no exception. So `a:b` is one plain scalar,
while `a: b` is not a scalar at all: it is read as a mapping (`a` → `b`), and
`run: echo static:` likewise becomes a mapping where GitHub expects a string,
which is what rejects the workflow. Quote the whole value whenever it contains `:`.
A local text review misses this: the value still reads as a plausible
shell command, and nothing in the repo parses workflow YAML locally (actionlint
is still a follow-up), so GitHub's parser is the first one to see the file and it
rejects the whole workflow. Recorded here because every new instantiation of the
required-check template can hit it: the template's worked example carries no
`:`-bearing echo strings, and the denylist workflow-I4 sanity leg cannot catch
parser-level rejections (they happen server-side).
