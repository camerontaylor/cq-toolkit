## Drill (a) — template self-test: docs-only PR through the queue (I4)

1. `main` initialized (README + static-check.yml), `merge-queue` branch created at
   the same commit (init-merge-queue bootstrap, idempotent ref create).
2. Branch protection on `main`: required context `static-check`, `enforce_admins`,
   `allow_force_pushes` (for drill b).
3. PR 1 = **docs-only** (README line) → `merge-queue`.
4. **I4 proven**: the docs-only PR received the required status — run
   https://github.com/camerontaylor/cq-scratch-h4-20260915/actions/runs/35007885231
   (`static-check`, `pull_request` event, **success**, 6s). No path filter suppressed
   it; a docs-only diff gets exactly the same required status as code.
5. PR 1 merged into `merge-queue` (merge commit `5c58d25`).
6. Promotion through the queue (doctrine: pure ff-push guarded by two merge-base
   checks):
   - guard 1 `merge-base --is-ancestor main merge-queue` → main IS ancestor → pure
     ff possible (no divergence);
   - `git push origin 5c58d25:refs/heads/main` → main `14a7027..5c58d25` ✓.
   - Refs-API alternative (`PUT /repos/…/git/refs/heads/main` with `force:false`)
     is the server-side equivalent; the local push exercises the same ff invariant.

## Drill (b) — divergence: force-diverge the queue, classify, recover

1. Force-diverged the queue: `git push --force origin diverge:refs/heads/merge-queue`
   where `diverge` = `14a7027` (old main) + one unrelated commit → queue `bad0622`.
2. Classification (sync-merge-queue triage): `merge-base --is-ancestor` both ways →
   neither main ⊆ queue nor queue ⊆ main → **DIVERGED**.
3. Recovery per the sync doctrine (merge-commit + conflict handling): `git merge
--no-ff origin/main` on the queue → merge commit `4ec51d0` (no conflicts here —
   the histories touch different files; the template's conflict path aborts and
   escalates needs-human, not needed in this drill).
4. Post-recovery verification: main IS ancestor of the queue again; queue pushed
   (`bad0622..4ec51d0`); final promotion ff-pushed `5c58d25..4ec51d0` to main.

## Incident found and fixed during the drill (recorded for the doctrine)

The first `static.yml` instantiation failed GitHub's workflow parser at
**startup** (run created, 0 jobs, no logs, run named by file path) even though the
YAML was locally valid. Bisected with probe workflows: the poison was a **colon +
space inside a plain-scalar `run:` value** (`run: echo "static: always reports
(I4 self-test)"` — `static: ` is a mapping-value indicator mid-scalar; YAML quotes
inside an unquoted scalar do not protect it). Fix: keep `:` out of unquoted step
values or quote the entire value (`run: 'echo …'`). This failure mode is
invisible locally (standard YAML parsers accept it — YAML 1.2 plain scalars may
contain colons not followed by space; `static: ` is followed by space, so it is
actually invalid — but local tools rounded the multiline value differently, which
is why it looked valid). Recorded here because every new instantiation of the
required-check template can hit it: the template's worked example carries no
`:`-bearing echo strings, and the denylist workflow-I4 sanity leg cannot catch
parser-level rejections (they happen server-side).
