# Mechanical tooling for agent-authored changes

Status: planning consensus reached with Opus (max reasoning), 2026-09-16. Implementation and compatibility preflight remain outstanding. Planning only; implementation is not authorized by this document.

## Objective and reasoning

Make incorrect assumptions cheap to detect and styles cheap to normalize. Prefer a small, reproducible set of deterministic commands whose failures identify correctness or architectural problems. Avoid rules that ask an agent to rewrite equivalent expressions. The supplied research supports this as an engineering hypothesis, not a controlled demonstration that particular lint rules improve agent success rates.

Target: Oxlint with native typed rules and integrated TypeScript checking as one static gate, stable TypeScript 7 for JS/declaration emission, Oxfmt, and the existing Vitest suite. Convert the custom ESLint architecture rules and their tests to Oxlint; do not keep an ESLint fallback lane. Add tuned Knip checks after the core migration is green. Keep actionlint as an independent follow-up, outside the core migration. No React configuration: this repository is a TypeScript SDK and CLI.

## Decisions

| Concern | Decision | Why |
| --- | --- | --- |
| Type checking and declaration emit | Oxlint typeCheck for the gate; stable TypeScript 7 for emit, pinned compatible versions | Reuse the Go type-analysis path; retain declaration/build validation |
| Syntactic and typed lint | Oxlint + matching supported oxlint-tsgolint, pinned | Fast native checks, including semantic async/type-safety rules |
| Architecture rules | Oxlint JavaScript plugin with conformance tests | Retain compressed architectural context while removing the ESLint toolchain |
| Formatting | Oxfmt, pinned | Mechanical normalization without model-driven style edits |
| Dead files/dependencies | Knip, tuned before gating | Detect forgotten wiring and obsolete dependencies without misclassifying SDK exports |
| Workflow checks (follow-up) | actionlint, pinned executable | Detect invalid expressions, contexts and workflow structure |
| Tests | Existing Vitest | Retain behavioral verification; lint cannot establish runtime correctness |

Do not add Biome alongside Oxc, another package manager, a task orchestrator or a monorepo affected-project graph. Keep `npm ci` and the existing lockfile. Upstream speed reports are motivation, not a claim about measured repo speed.

## Compiler configuration

Keep `strict: true`; add `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noFallthroughCasesInSwitch` and `noImplicitReturns`. `useUnknownInCatchVariables` already follows from strict; it can be documented without a redundant setting. Keep skipLibCheck initially: changing dependency declaration validation is a separate concern.

These flags expose missing collection elements, absence versus explicit undefined, inheritance drift and incomplete control flow. Repair real assumptions with narrowing, correct optional construction and complete branches. Do not use casts, postfix assertions, broad undefined unions or baseline growth just to get green. Runtime validation remains necessary at untrusted input boundaries.

Use the released `typescript` package for TS7, not a native-preview nightly. Before switching, establish compatibility with Node 24, NodeNext resolution, declaration emit, Vitest/config tooling, the ratchet diagnostic parser and any consumers of the programmatic TypeScript API. Confirm the supported runtime contract: the current @types/node 26 versus CI Node 24 mismatch can allow APIs unavailable at runtime. Align the Node type major with the supported runtime unless a documented multi-version support policy requires another choice. Where a tool still needs the legacy JS compiler API, explicitly retain an isolated TS6 compatibility dependency only if needed and documented; it must not silently become the authoritative compiler.

Prefer `oxlint --type-aware --type-check` as the one full static invocation. Official Oxlint documentation explicitly supports replacing a separate `tsc --noEmit` this way. The architecture is Oxlint plus tsgolint using typescript-go; do not assume it shells out to the workspace's installed tsgo/tsc executable or shares the identical revision. Build still uses the pinned native compiler to emit JS/declarations; this is not a second diagnostic ratchet, although an ordinary emit build also checks types. A type-grounded build failure after a green static gate is a checker-divergence signal: investigate the minimized case and versions/configuration under the contradictory-type-facts procedure, rather than blindly patching source or disabling build checking. Both the gate and build must pass.

Retain the existing zero type-error baseline and fail-closed wrapper contract while replacing the diagnostic producer. Parse a documented structured Oxlint output format; classify compiler diagnostics separately from lint diagnostics. Do not feed merged lint/type counts into the existing type baseline, and do not reuse the `error TS` text regex for a different format. Any enabled lint error fails independently. Missing executables, crashes, malformed/truncated output, unknown diagnostic categories and configuration/project-loading errors must fail, not count as zero. Baseline updates cannot hide lint/tool failures or increase the type baseline. Keep existing fake-tool failure tests and add real combined-tool fixtures.

Before selecting the integrated gate, prove coverage of every intended tsconfig input, including errors in files not selected by ordinary lint traversal, imported dependencies, TS config files, and applicable declarations; verify compiler-option and module-resolution failures are surfaced. Compare compiler diagnostics to the pinned standalone TS7 on a focused known-error corpus under this repo's exact settings. This is migration evidence, not two permanent checks. Confirm suppressions/ignore directives cannot silently exempt compiler errors that the former ratchet would catch. Validate JSON schema, diagnostic categories, known counts, zero-result success and process failure behavior. Pin compatible tool versions and repeat this conformance evidence on relevant upgrades. Include declaration compatibility in preflight: gate accepted public-API fixtures, emit them with the standalone TS7 build, compare the declarations with the reviewed pre-migration/expected API contract, and compile focused consumer fixtures. Oxlint does not emit declarations, so there is no Oxlint declaration artifact to diff against tsc. The comparison is against the intended published contract and prior compiler output; investigate unexpected drift explicitly rather than assuming a green static gate validates declarations.

If combined mode cannot satisfy that contract, retain the direct native-compiler ratchet and typed Oxlint separately, with the specific demonstrated gap documented. That fallback is one compiler ratchet plus lint, not two compiler ratchets. Do not retain duplicate whole-project typechecking by default merely because the old command existed.

Update the ratchet implementation, its fixtures, `npm run typecheck`, all executable references/plan fixtures, CI templates and affected AGENTS.md instructions atomically in PR 3. Verify installed executable ownership after fresh npm ci, especially if a legacy compiler API dependency remains. No baseline relaxation.

## Rule policy

Use explicit reviewed rules, error or off. Do not turn on all rules or strict/stylistic presets wholesale. Use Oxlint correctness recommendations as an inventory input, then explicitly select the effective error rules and disable overlapping or unwanted defaults; do not inherit an unreviewed warning category. Disable overlap already handled better by the compiler or formatter. Each additional gate must have a concise correctness rationale. New baseline-free errors should be repaired before gating; do not leave warnings as a permanent migration state.

Enable native `typescript/` rules, subject to checking the pinned release's supported names/options:

- Async: `no-floating-promises`, `no-misused-promises`, `await-thenable`. Set floating-promises `ignoreVoid: false`, so `void promise` is not an escape hatch. Keep promise-returning callbacks checked; scope exceptions to demonstrated synchronous API contracts, not a blanket disabled checksVoidReturn. Deliberate background work needs an explicit rejection-handling contract: awaiting, returning to an accountable caller, or attaching a rejection handler recognized by the rule. Bare void does not handle rejection. Do not replace bare void with disable comments or add a custom helper/rule unless an actual recurring use case warrants it. Lint acceptance is not proof that a rejection handler itself cannot fail.
- Type holes: `no-explicit-any`, `no-unsafe-assignment`, `no-unsafe-argument`, `no-unsafe-call`, `no-unsafe-member-access`, `no-unsafe-return`. Use unknown and validate at boundaries. Target these rules in tests too, but first classify test findings in a one-time report. Fix accidental unsafe flows; keep intentional malformed-input construction at narrow, documented fixture boundaries (a small helper only when it reduces duplication). Do not generate a blanket test-directory exemption or a spray of suppressions. If a specific rule has systematic false positives in a fixture family, record and scope that exception before activating it; ordinary tests remain covered.
- State space: `switch-exhaustiveness-check`, with `considerDefaultExhaustiveForUnions: false` and `allowDefaultCaseForExhaustiveSwitch: true`, so a default does not count as exhaustive handling of a union. Allow a defensive default where runtime input can violate static types; it must not hide a missing union member.
- Suspicious logic: evaluate `no-unnecessary-condition` in a one-time migration report, not permanent warning output. Classify findings as real assumption errors, legitimate trust-boundary checks or analysis limitations. Activate it only for scopes where correct code remains naturally expressible without widespread suppressions or removed runtime validation; otherwise leave it off and record why. No arbitrary finding-count ratio determines correctness. This assessment follows runtime-type alignment and stricter flags.

For the integrated gate use `options.typeAware: true` and `options.typeCheck: true`, or equivalent explicit full-gate CLI flags over one root config. The fast command disables both. Built-in typed rules supply type information; custom JavaScript plugins remain syntactic checks. Record the pinned tsgolint checker revision/compatibility and supported tsconfig options. A green compiler does not invalidate a stricter lint finding. For genuinely contradictory type facts, minimize the example and compare pinned tools/configuration; fix the source bug or narrowly document a confirmed analyzer limitation rather than automatically preferring either tool.

Initially off: `strict-boolean-expressions`, `no-unsafe-type-assertion`, blanket postfix-non-null bans, explicit-function-return-type, explicit-module-boundary-types, consistent-type-definitions, member-ordering, sorting rules, generic complexity/line/parameter limits, and preference rules requiring equivalent rewrites. Public SDK contracts can still have intentional signatures. Do not treat potentially semantic changes such as replacing || with ?? as unattended style fixes.

Formatting and fixes are distinct: Oxfmt owns layout. Only reviewed safe lint fixes belong in an automatic fix command; do not enable dangerous/suggestion fixes. Run semantic checks after any fixes. Keep suppression comments narrow with reasons, flag unused directives where supported, and extend the existing added-lines suppression detector to `oxlint-disable` while preserving ESLint detection. A suppression reason is review context, not proof that bypassing the rule is safe.

## Agent command contract

Expose a small interface:

- `npm run fix -- <file...>`: approved safe lint fixes followed by Oxfmt write, so fixes do not leave formatting dirty. Require an explicit owned-file list; no implicit whole-repo rewrite. Pass paths as arguments, handle spaces/deletions safely and reject an empty list. Implement this as `scripts/fix.mjs`, spawning the pinned tools with an argv array: npm cannot reliably forward one file list to both halves of a compound shell script. A one-time whole-repo formatting migration is a separate explicit operation.
- `npm run check:static`: the authoritative wrapper running Oxlint once for syntactic rules, architecture rules, typed rules and compiler diagnostics, enforcing the existing type baseline. Read-only.
- `npm run lint` and `npm run typecheck`: compatibility aliases to check:static once PR 3 lands; document that either validates the whole static gate. Do not invoke both inside an aggregate or CI job.
- `npm run format:check`: Oxfmt check; read-only.
- `npm run check`: format check, check:static once, tests, and tuned dependency/workflow gates when activated. Preserve nonzero exits and show actionable file/rule diagnostics. Avoid log truncation that can hide failure.

The inner loop accepts an explicit list of owned changed files for formatting and syntactic lint, runs targeted tests, then runs this package's typecheck when relevant. Expose `npm run lint:fast -- <file...>` using a syntactic config/CLI override that disables both typeAware and typeCheck. Use the same single root lint configuration with supported CLI flags that disable typed mode; verify those flags in preflight. If unsupported, revise the command design before implementation rather than inventing duplicate policies. Paired fixtures must report a typed-only violation and a compiler-only violation under the full gate, neither under fast lint, while a syntactic violation fails both. This proves diagnostic behavior, not absence of process startup; verify startup separately with a temporary failing/counting shim at the pinned tsgolint launch point or equivalent process tracing. A startup claim requires that evidence. Never infer correctness from only linting a changed file: dependents can break. This is one package, so affected-package checking is the whole package. No automatic full-repo rewrite on every agent turn or in shared worker workspaces.

The pre-review loop runs check:static once, test, formatter check, build, smoke, denylist/self-test and any activated additional gates. Keep validation checks non-mutating to tracked source; build/smoke may write their normal ignored outputs. Formatting happens before those checks, not by asking an agent to repair commas. Avoid mandatory commit hooks: agents use the documented commands and CI remains authoritative.

Record a simple before/after wall-clock comparison on the same machine for the full gate and the fast lint command. Investigate a material regression; do not build a benchmark harness. The two-loop split is a workflow decision, not a claim supported by unmeasured speedup figures.

## Secondary mechanical checks

Knip: configure actual SDK/CLI entries, package exports, scripts, tests, dynamically loaded registry/provider paths and the new lint plugin. Investigate findings before deleting anything. Start gating unused files, dependencies and unresolved imports only after a clean calibrated run. Public exports are intentional entry points; do not delete them because no in-repo consumer exists. Add export analysis only where internal usage is accurately modeled. Verify an intentionally unreferenced file in an isolated fixture project is reported, so entry configuration cannot accidentally include every file. Avoid broad ignore lists that make the check decorative.

Actionlint (separate follow-up, not a prerequisite for core completion): run on instantiated workflows using a pinned binary/checksum and a documented local installation path. Never download an unpinned tool during a check. Missing tools must fail with an installation instruction, never silently skip. Pin release checksums per supported platform, including local macOS and CI Linux. Decide explicitly whether ShellCheck integration is enabled and provision it consistently; do not let CI/local behavior depend on incidental PATH contents. Template placeholders are not valid workflow input. Fix templates and reinstantiate, preserving required check names and triggers.

Oxfmt: use conservative existing-style options (including single quotes and semicolons if confirmed against the source), disable optional import/package/object reordering. Exclude dist, coverage, generated fixture artifacts and instantiated workflow YAML from independent rewriting; templates are the source. Make a one-time formatting-only change separable from semantic fixes for review. Use the PR boundaries below; any re-splitting happens during preflight, before review begins.

## Acceptance and stop conditions

Done means all mandatory gates pass with zero type baseline, both architecture policies demonstrably fire under the real Oxlint CLI, typed rules detect representative async/any/exhaustiveness mistakes, maintained files are discovered, formatting is deterministic, package exports/declarations/CLI still work, and CI and local verification use the same pinned underlying gate commands. Add focused negative fixtures for new enforcement and ratchet failures; do not add tests mirroring every config line. In particular, an isolated real combined-tool project with known compiler errors must run through the ratchet and report the expected nonzero diagnostic count and fail against a zero baseline; a repaired counterpart must pass. Fake tool tests alone cannot validate a diagnostic-producer migration. Compare against standalone TS7 for the migration corpus, but do not add a permanent duplicate noEmit gate. Exhaustive-switch lint covers switches, not arbitrary if/else or lookup-table control flow; use ordinary never-based compiler checks where those boundaries need exhaustiveness.

Stop for unsupported plugin semantics, native compiler/API incompatibility, unexplained public declaration changes, or a gate that appears green because files were omitted. Record the specific evidence and revise the plan. Do not raise baselines, disable established invariants, remove valid runtime validation, or add broad suppressions to force completion.

Before any implementation PR, follow docs/coderabbit-review.md: pin one immutable merge-base against the explicit intended target (normally origin/merge-queue); run exactly two successful full-diff CLI review-and-address cycles with the same base; record reviewed HEAD and dirty-diff identity; run deterministic gates before cycle 1, between cycles and after cycle 2. Failed/skipped runs do not count. Resolve valid critical/major findings; post-cycle-2 fixes require independent non-author review before a ready-to-merge claim. The Opus plan consultation does not substitute for these reviews. No PR or ready-to-merge claim is part of this planning task.

## Alternatives and decision record

- Keep ESLint for custom rules: lower migration risk, but contradicts the requested complete conversion and retains two engines/test stacks. Rejected as target.
- Biome plus ESLint/typed lint: capable but adds overlapping ownership and retains the custom-rule migration question. Rejected for this repo.
- Separate native compiler noEmit plus Oxlint: retain only if a demonstrated coverage/output compatibility gap blocks the integrated ratchet. Oxlint documents integrated typechecking as a supported replacement, so separation is no longer the default. Preserve the ratchet contract independently of which executable supplies its diagnostics.
- Maximal strict/stylistic presets: broad coverage, but forces equivalent rewrites and unstable rule drift. Prefer a pinned explicit semantic policy.

Consequences: tighter correctness constraints may require meaningful source repairs; Oxc plugin upgrades need conformance tests; native compiler integration needs a compatibility preflight. The benefit is one local lint engine, automated style, and executable architectural context with clear failure ownership.
