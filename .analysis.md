# Replace review.address repository authority with checkout ownership

Date: 2026-11-07. Analysis, not product changes or an approved implementation spec.
Code pin: cq-toolkit `8ac65fbf55d6732b063293bf255a19287f77d6d3`.
All `src/`, `test/` and `docs/` file:line references below mean that pin,
not this research repository. Verified = read in pinned source; proposed/inference
= architectural judgement. Host inventory is dispatcher evidence, not independently inspected.

## Recommendation

Remove repository-lifetime exclusion and the hash-chained authority store.
Use a stable per-checkout kernel lock, separate registry entries, and explicit
remote expected-head comparisons. Preserve writer draining, failed-attempt
retention and identity-checked restoration. Git command locks cannot replace
those multi-command lifetime guarantees.

The candidate is sound for cooperating processes on local Linux/macOS storage,
with two corrections: lock a persistent logical worktree slot **before creation**,
and account for surviving subprocesses when Node dies. An unlocked checkout
proves neither clean contents nor that an orphan editor has stopped.
A bare replacement of AddressOwnership with `flock` loses these guarantees.

Production scope is smaller than the class suggests. Verified:
`addressMany.ts:119–125` creates unique independent clones; `:336–360` passes
original-common-dir coordination to each address factory. `address.ts:3338–3355`
uses a per-PR mutex there, while `withAddressOwnership` uses each clone's own
common dir (`addressOwnership.ts:1535–1553`). Bulk jobs do not all share one store.
`AddressOwnership.address` and its durable resource-claim pathway have **no
production caller** outside their own module (source-wide symbol search).
The child API is primarily exercised by tests. Direct production leases do not
carry the common-dir registry (O:1412); `address.ts:2859–2860` falls back to
journal-local `worktrees.json`. Thus common-store exclusion is live, while its
shared-registry/child-claim integration is dormant in production. Do not design
migration as if addressMany were still that older shared-owner executor.

## Shared Git state: what command locks do and do not cover

Verified resolver names are `refs/heads/cq-review/pr-N` (W:87–96), not a
hypothetical `cq-review-*`; fetch writes `refs/cq-review/pr-N` (W:475–492).
Acquire PR-slot lock before fetch, otherwise a same-PR contender can change
that ref between fetch and rev-parse. Different PR fetches may both write
FETCH_HEAD; existing code deliberately does not consume it (W:475–478).
Use `--no-write-fetch-head` if compatible with other consumers.

Git shares ordinary refs, object storage, packed-refs and usually config across
linked worktrees; HEAD/index are per worktree. Its file/ref locks protect a
command's update, not “scan, check, later delete/create” transactions.
[Git worktree reference](https://git-scm.com/docs/git-worktree), fetched 2026-11-07.
Inference/proposal: distinct PR-slot worktree adds need no repo lifetime lock;
conflicting Git operations must fail cleanly/retry after re-reading identity.
No repo-wide `worktree prune` is called in W:435–758: “pruning” there means
registry deletion and targeted removal. Future global prune must respect active
worktrees; `git worktree lock` can prevent administrative pruning but is not a
writer mutex. Do not add global prune to the address hot path.

Do not mutate shared config or packed-refs by direct file editing. Let Git lock
its own updates; narrow ref-CAS operations are appropriate when an algorithm
requires expected-old-value semantics. Distinct worktrees sharing one branch
still share a ref: prohibit that layout in cooperative resolution, retaining
Git's existing refusal to add a checked-out branch (W:43–51,669).
A registry directory enumeration has no atomic cross-checkout snapshot; no
source consumer found requires one beyond discovery followed by validation.

Push currently uses plain fast-forward `HEAD:<headRefName>`
(`review-loop.ts:740–756`), for both publishing and push-before-reply.
Use explicit `--force-with-lease=refs/heads/<ref>:<expectedSHA>` against the
**head repository**, with explicit destination ref, not the tracking ref.
[Git push reference](https://git-scm.com/docs/git-push), fetched 2026-11-07.
This enforces tip equality across hosts; it does **not** assert ancestry, target
authorization or remote-side thread/report idempotency. Preserve fast-forward
ancestry checks unless rewriting history is intentionally supported. Advance
the expected SHA to the confirmed published tip for subsequent pushes; after
an uncertain network result read the remote and reconcile before any retry or
reply. Do not refresh a stale expected SHA and replay old work automatically.
Remote branch aliases, PR comments and re-review submissions need their current
identity/idempotency checks even when the push CAS succeeds.

## Steelman: why the present design exists

The author's commit `c437d514` says detached work/lost ownership prevent proving
quiescence. [PR #681](https://github.com/camerontaylor/cq-toolkit/pull/681)
explicitly covers worker edits, cancellation, restoration, report finalization,
and “Cancellation settles writers and retains evidence without publishing or replying.”
[PR #1172](https://github.com/camerontaylor/cq-toolkit/pull/1172) repairs finite
store exhaustion while preserving active/quarantined barriers, crash evidence
and one-generation completion verification; [#1183](https://github.com/camerontaylor/cq-toolkit/pull/1183)
fixes quiet diagnostics and cancellation identity. Bodies fetched using
`env -u GITHUB_TOKEN gh` on 2026-11-07; these are author statements, not deployment proof.

| Rationale | Does it still apply? |
|---|---|
| Time is not proof of death; abort is not proof that a writer stopped (O:277–284,1292). | Yes on all Linux hosts and macOS. Event-loop stalls, SIGSTOP and VM suspend can exceed heartbeat periods. Kernel-held locks survive pauses without heartbeat reclaim. |
| PIDs do not authenticate an owner; PID reuse/foreign hosts and differing TMPDIR defeat simple probes (`docs/adr/0003-governed-runner.md:263–295,456`). | Yes, but this ADR concerns the plan/budget lock, not a mandate for this authority chain. Same canonical kernel lock avoids PID-based reclaim entirely. ADR itself permits carefully established dead-holder recovery: do not cite it as banning all liveness recovery. |
| Parent cancellation can leave promises/processes alive and unbounded write sets (O:1047–1069,1283–1302). | Yes. This is the strongest objection to a naive flock rewrite; retain drain/opaque-refusal semantics and handle orphan writers. |
| Store tampering/replacement or release failure means ownership is uncertain (O:147–175,729–850). | Same-user interference is possible; keep path/inode checks. No advisory lock stops an agent ignoring it. A sandbox/capability boundary and constrained push path address that separate problem. |
| Old binaries ignore the guard (O:284). | Still true: neither old mutex directories nor flock exclude one another. Avoid overlapping protocols during migration. |
| Unsupported directory fsync/no-follow fails closed (O:149,181–185). | Present implementation requires strong filesystem primitives. No evidence found that network filesystems motivated this owner or are used by the fleet. Do not invent that requirement. |

No ownership-specific ADR or README rationale for rejecting flock was found.
The README documents operational evidence/report semantics; ADR-0003's budget
accounting has different durability requirements and should remain unchanged.
Dispatcher identifies Linux triton, uranus, saturn, pluto, ceres and macOS use.
Actual worktree mount types and OrbStack host-shared mount behavior were not
measured. Linux guest-local storage is the proposed supported baseline;
VM suspend keeps kernel state, whereas reboot/power loss releases locks but
leaves partial files. Shared VM snapshots/clones are not a distributed lock.

## Node/TypeScript mechanism

Node core has no public flock API in its [fs surface](https://nodejs.org/api/fs.html)
(fetched 2026-11-07). Numeric open flags do not add Linux flock.

| Option | Assessment / proposed choice |
|---|---|
| `fs-ext` native addon | Direct asynchronous/nonblocking flock on an fd; Linux and macOS syscall path. Current upstream package is 2.1.1, NAN-based, with node-gyp install. Existing API, but compiler/toolchain, Node ABI, prebuild and maintenance burden; a low engine floor is not modern compatibility proof. Do not label it “maintained” without release/CI validation. |
| Small Node-API addon | Same syscall with stable addon ABI and platform builds; lower API surface but ownership of packaging/prebuild/security updates. Better long-term only if existing package cannot meet supported Node versions. |
| macOS `O_EXLOCK` | Darwin supports atomic exclusive lock at open, plus O_NONBLOCK. Node does not document/export this flag in its fs constants list; Darwin numeric flag via numeric fs.open is a possible platform-specific workaround, requiring actual Node/libuv/macOS validation. Do not assume Linux values. |
| Linux OFD `fcntl` locks | Good fd-lifetime semantics, Linux-specific API and native binding still needed. Do not mix with flock: on local Linux they are independent lock families. Traditional POSIX process locks have different close behavior. No portability advantage here. |
| Spawn `flock(1)` around the full CLI | Good Linux operational wrapper, but SDK callbacks are not whole CLI processes and macOS lacks util-linux flock by default. A package/binary prerequisite, not a portable SDK solution. |
| Helper child holding the lock | Ready/EOF protocol and helper lifetime become another authority problem: helper death can unlock while parent still edits; parent death need not kill helper. Adds IPC, subprocess/sandbox permissions, cancellation and packaging complexity. Reject as default. |

Sources fetched 2026-11-07: [fs-ext API](https://raw.githubusercontent.com/baudehlo/node-fs-ext/master/README.md),
[package](https://raw.githubusercontent.com/baudehlo/node-fs-ext/master/package.json),
[Apple open](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/open.2.html),
[Darwin flags](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/fcntl.h),
[OFD semantics](https://man7.org/linux/man-pages/man2/F_OFD_SETLK.2const.html),
[util-linux flock](https://man7.org/linux/man-pages/man1/flock.1.html).

Recommend a private adapter using `fs-ext` nonblocking exclusive flock initially,
conditional on a named Linux/macOS supported-Node packaging smoke test in CI.
Mac uses the same native syscall; O_EXLOCK is the fallback experiment if addon
packaging cannot support it, not an automatic unlocked fallback. Unsupported
platform/install/sandbox denial returns an explicit unsupported error. Do not
spend libuv threads indefinitely waiting: fail fast or bounded abortable retries.
Containers need write access to the common-dir lock namespace, and permission
to load the native addon; no privileged service or network is required.

Linux flock is advisory, tied to the open file description and released on last
close; duplicated/inherited descriptors keep it alive. NFS may emulate it with
fcntl, with mount/server-dependent behavior, including local-only options.
[flock syscall reference](https://man7.org/linux/man-pages/man2/flock.2.html), fetched 2026-11-07.
Do not repeat fs-ext README's unqualified “no NFS” assertion as modern Linux fact.
Proposal: support local storage first; network/FUSE/SMB/OrbStack shared mounts
need a two-process exclusion/crash test on their actual mounts before claiming support.

Overlay identities may change during copy-up ([kernel documentation](https://docs.kernel.org/filesystems/overlayfs.html),
fetched 2026-11-07). Create lock files in the writable layer before use; require
all participants to see the same inode. A bind mount of the same underlying
file can share exclusion; separate overlay upper layers/copies cannot.
These are deployment inferences, not tested fleet filesystem guarantees.
No prototype, addon installation or product tests were run for this analysis.

## Lock placement and crash recovery without the authority store

Proposed namespace: `<canonical-common-dir>/cq-review/slots/pr-N.lock` and
`pr-N.json` for resolver metadata. Persistent lock inode is outside both the
checkout and `worktrees/<name>` admin directory: creation/removal cannot replace
it. Local mode additionally keys a lock by canonical checkout Git-dir identity
(including main checkout). Unique candidate worktrees belong to the parent run;
any independently reusable candidate also needs its own checkout exclusion.
Use one canonical lock ordering: PR slot, then actual checkout; nested loop
reuses held context. Register failed-attempt refs with Git create-only CAS,
retaining the collision retry in E:35–50 rather than adding a global ref lock. These are resource locks, not a repository lifetime mutex.

Never rename or unlink a live lock file; replace only metadata through unique
temp + rename. Removing a locked inode permits another process to lock its
replacement. A per-worktree file inside its admin dir alone misses admission
before creation and can split exclusion on remove/recreate. Serialize resolver
operations by PR label even when headRefName or worktreeRoot changes.

Crash cases and proposed behavior:

1. Graceful cancellation: stop dispatch, drain actual writers, retain failed
   bytes in commits/refs before verified restore and final report; close lock
   only after terminal subprocesses close. Preserve E:677–875, O:1047–1159.
2. Abrupt Node death with no surviving writer: kernel releases fd, edits/index,
   candidate trees and unpushed commits remain. Under the next lock inspect
   tracked/untracked/ignored files, index/HEAD and ahead commits; do not silently
   reset or reuse a dirty tree. Existing non-forced removal and unpushed guard
   (W:602–645) stay. Same-HEAD reuse (W:529–548) needs an explicit dirty-state
   check: it currently does not establish cleanliness.
3. Node death with surviving editor/Git child: parent-only flock releases too
   early. Prefer passing the held fd explicitly to controlled writer processes
   and retaining it throughout writer lifetime; release by **closing**, not
   explicit LOCK_UN that can unlock shared descriptions. Node subprocesses
   normally do not inherit arbitrary fds. Audit driver/sandbox spawns, detached
   jobs and descendants: an fd cannot be assumed to survive an exec chain.
4. Where writer lifetime cannot be tied to the fd, keep an incomplete-run flag
   in the single checkout metadata file, durably written before dispatch and
   cleared only after actual drain; persistence failure refuses dispatch. A successor refuses that checkout until positive quiescence
   and contents are reconciled; this is not a hash chain or stale lock. It
   deliberately gives up automatic crash recovery for opaque writers. If the
   owner rejects even this metadata, require process-tree containment instead;
   clean status alone cannot prove that an orphan will not write later.
5. Power loss may tear source/index/report writes. Keep bytes and stale metadata;
   reconstruct from Git objects/failed refs where available, otherwise require
   attended inspection. Lost in-memory receipts cannot be recreated with their
   original authenticated provenance. Never claim terminal settlement occurred
   after SIGKILL. Durable failed-attempt refs already made remain useful;
   do not garbage-collect clones containing unresolved work.

This preserves recoverability without durable authority history, while losing
the repo-wide forensic promise. Kernel exclusion solves ownership lifetime;
content recovery and rogue-writer authorization remain distinct problems.

## Owner decisions / remaining evidence

- Accept local-filesystem-first support, or require NFS/SMB/FUSE/shared OrbStack
  mounts? Actual mount and macOS addon behavior needs verification before shipment.
- Accept a native dependency/toolchain/prebuild burden? Recommended: fs-ext
  adapter first; replace with a small Node-API binding only for demonstrated need.
- For opaque orphan writers, accept checkout-local incomplete metadata/manual
  recovery, or require reliable process-tree containment? Neither automatic
  flock release nor a clean status check alone preserves current semantics.
- Keep original-repo per-PR exclusion for unique bulk clones, or accept redundant
  computation and rely on remote CAS? Recommended: keep existing behavior as a
  cheap PR-slot lock; this is not repo-wide exclusion.
- Preserve fast-forward-only publishing, or permit deliberate history rewrites
  under a lease? Recommended: preserve ancestry policy; lease equality is extra
  correctness, not authorization to rewrite unrelated history.
- Is checkout exclusion promised across generic fix and the whole dev.cycle,
  or only participating review operations? Current repo owner never provided
  that broader promise; sandbox/push restrictions remain separate.

## Owner rulings (2026-11-07, AskUserQuestion)

- Granularity: no repo-level lock. Exclusion is per PR slot / per checkout. Registry is one metadata file per slot, not a shared JSON map (owner suggestion, adopted above).
- Orphan writers: pass the held lock fd to controlled writer processes; where that cannot be guaranteed, use a single incomplete-run flag in the slot metadata that blocks reuse until reconciled.
- Mechanism: `fs-ext` flock behind a private adapter on Linux and macOS, gated by a CI packaging smoke test; macOS `O_EXLOCK` only as a fallback if packaging fails.
- Filesystems: local disks only. Network/FUSE/shared mounts are unsupported until tested on the actual mount.
- Bulk addressing: keep the per-PR slot lock in the original repo for unique clones; the leased push remains the cross-host guarantee.
- Not yet ruled (defaults from the recommendation stand): fast-forward-only publishing is kept; checkout exclusion covers review.address and review-loop only, not generic fix or the whole dev.cycle.
